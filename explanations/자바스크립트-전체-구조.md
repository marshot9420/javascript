다만 위 트리는 완전한 포함 관계가 아니며, 이 지도는 개념을 걸어둘 분류 틀이지, 모든 것이 부모 아래에만 고립된 구조는 아니다. 기존 분류에서도 명세·호스트·엔진 규칙을 구별해 놓았듯이, 실제 현상 하나는 여러 가지를 가로지른다.

예를 들어, `Promise.then()` 콜백 실행은 다음 세 가지가 연결된다.

```
ECMAScript
→ Promise reaction과 Promise Job의 의미 규정

V8
→ Promise 객체와 콜백 JavaScript 코드를 구현·실행

브라우저 또는 Node.js
→ microtask 처리 시점과 event loop 통합
```

따라서 가장 좋은 구조는 계층 트리 + 가지 사이의 연결선이다.

# 자바스크립트 공부 분류

자바스크립트를 알아 볼 때, 다음과 같이 분류할 수 있다.

- ECMAScript
- V8 자바스크립트 엔진
- 호스트 환경
  - 브라우저
  - Node.js

ECMAScript 명세는 JavaScript가 무엇을 해야 하는지를 규정하고, V8은 그것을 실제 컴퓨터에서 어떻게 구현하는지를 보여준다.

## 1. ECMAScript 명세: 무엇이 일어나야 하는가

[[ECMAScript 명세]]는 무엇이 일어나야 하는지를 규정한다. 다음 개념들은 단순한 설명 자료가 아니라 **모든 호환 JavaScript 구현이 지켜야 할 의미와 동작 규칙**이다.

- 문법적으로 어떤 코드가 유효한가
- 표현식을 어떤 순서로 평가하는가
- 값과 타입이 어떻게 동작하는가
- 객체의 프로퍼티를 어떻게 찾는가
- 함수 흐름과 `this`가 어떻게 결정되는가
- 변수 바인딩과 스코프가 어떻게 동작하는가
- 실행 컨텍스트를 어떻게 모델링하는가
- `Promise` 반응이 어떤 `Job`을 만드는가
- 예외와 반환을 어떻게 전달하는가

예를 들어 명세는 `var` 바인딩이 환경 레코드가 인스턴스화될 때 생성되고 `undefined`로 초기화된다고 규정한다. 또한 실행 컨텍스트를 "코드의 런타임 평가를 추적하기 위한 명세상의 장치"라고 명시한다.
[ECMAScript 문서](https://tc39.es/ecma262/multipage/ecmascript-language-statements-and-declarations.html?utm_source=chatgpt.com)

## 2. V8 엔진: 그 규칙을 어떻게 실제로 구현하는가

[[V8 자바스크립트 엔진]]은 ECMAScript가 요구하는 결과를 실제 CPU와 메모리 위에서 만들어낸다

- 소스 코드 파싱(parsing)
- AST(Abstract Syntax Tree, 추상 구문 트리) 및 내부 표현 생성
- 스코프 분석
- 바이트코드 생성
- 인터프리터 실행
- 실행 정보 수집
- JIT(Just-In-Time) 컴파일
- 객체의 실제 메모리 표현
- 함수 호출 프레임 관리
- 최적화와 최적화 해제
- 메모리 할당과 가비지 컬렉션

V8 문서에 따르면 V8은 JavaScript 소스 코드를 컴파일하고 실행하며, 객체의 메모리 할당과 가비지 컬렉션을 담당한다. V8의 Ignition은 파서가 만든 AST를 받아 바이트코드를 생성하고, 인터프리터가 그 바이트코드를 실행한다.
[V8 문서](https://v8.dev/docs)

V8이 답하는 질문은 다음과 같다.

- 이 표현식은 어떤 바이트코드가 되는가?
- 함수 호출은 실제로 어떤 프레임을 사용하는가?
- 객체 프로퍼티는 메모리에 어떻게 저장되는가?
- 프로퍼티 접근을 왜 inline cache로 최적화하는가?
- 어떤 코드가 기계어로 최적화되는가?
- 왜 최적화된 코드가 다시 deopt되는가?
- 객체는 언제 GC의 수거 대상이 되는가?

따라서 실제 구현 구조를 보려면 V8을 공부하는 것이 나을 수도 있다. 다만 어쨌든 "무엇이 일어나야 하는가"는 ECMAScript 명세를 보아야 할 것이다.

## 3. 명세 개념과 V8 구현은 일대일 대응하지 않는다.

여기가 가장 중요한 부분이다.

```
ECMAScript 명세              V8 구현

Execution Context       ↔    실제 실행 프레임·내부 상태
Environment Record      ↔    Context·ScopeInfo 등의 내부 구조
표현식 Evaluation       ↔    바이트코드·인터프리터·컴파일된 기계어
객체 내부 메서드        ↔    object layout·Map·descriptor·inline cache
Number 값               ↔    Smi·HeapNumber 등의 내부 표현
Promise Job             ↔    microtask 실행을 위한 V8·호스트 연결
```

여기서 `↔`는 **개념적으로 대응한다**는 뜻이지, 양쪽이 동일한 구조라는 뜻은 아니다.

예를 들어 명세의 실행 컨텍스트는 런타임 평가를 설명하는 명세 장치이다. V8이 반드시 `ExecutionContext`라는 객체 하나를 생성해서 명세의 모든 필드를 그대로 저장하는 것은 아니다. V8은 동일한 관찰 결과만 보장한다면 내부 구조를 자유롭게 최적화할 수 있다.

## 4. 실제 작동 원리에도 여러 깊이가 있다.

실제 작동을 어디까지 내려가 볼 것인지에 따라 층위가 달라진다.

### JavaScript 프로그램의 실제 작동

1. ECMAScript 명세
   - 어떤 의미와 결과가 보장되는가
2. V8
   - 언어 규칙을 어떤 자료구조와 실행 파이프라인으로 구현하는가
3. 호스트
   - Chrome
   - Node.js
     - V8을 언제 호출하고 외부 기능과 어떻게 연결하는가
4. 운영체제
   - 스레드·메모리·파일·소켓·시스템 호출
5. 하드웨어
   - CPU 명령어·레지스터·캐시·RAM

그러므로 V8을 공부하면 JavaScript 언어 구현의 실제 작동 원리를 볼 수 있다. 하지만 다음과 같은 부분까지 전부 V8로 설명되지는 않는다.

- `setTimeout`의 시간 측정
- 파일 비동기 읽기
- 네트워크 소켓
- 브라우저 렌더링
- Node.js 이벤트 루프 단계
- 운영체제 스레드와 시스템 호출

이것들은 호스트와 운영체제까지 내려가야 한다.

## 5. 명세와 엔진을 비교하며 보면 무엇이 드러나는가

예를 들어, 다음 코드를 보자.

```js
const result = user.score + 1;
```

### ECMAScript 관점

1. `user` 식별자 바인딩을 찾는다
2. `user`의 값을 얻는다.
3. `score` 프로퍼티 참조를 평가한다.
4. 프로퍼티 값을 얻는다.
5. `1`과 덧셈한다.
6. `result` 바인딩을 초기화한다.

이 관점은 **어떤 결과가 나와야 하는지** 설명한다.

### V8 관점

1. 코드를 파싱한다.
2. 바이트코드를 생성한다.
3. `Ignition`이 바이트코드를 실행한다.
4. `user`의 실제 객체 표현을 확인한다.
5. inline cache를 통해 `score` 위치를 빠르게 찾을 수 있다.
6. 실행 정보를 수집한다.
7. 반복 실행되면 최적화 컴파일 대상이 될 수 있다.
8. 기존 가정이 깨지면 최적화가 해제될 수 있다.

이 관점은 그 결과를 **어떻게 효율적으로 만들어내는지** 설명한다. V8은 인터프리터 실행 중 피연산자와 연산에 관한 피드백을 수집하여 후속 최적화에 활용할 수 있다.
