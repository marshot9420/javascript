# 순환

- 무언가를 만들고 문제가 발생하면 이론을 공부하고 해결한다
- 이론 공부 과정에서 떠오른 아이디어는 즉각 반영해 실행한다.
- 그 과정에서 더 깊이 들어간다.

```txt
무언가를 만든다
→ 예상과 실제가 어긋난다
→ 의문이 생긴다
→ 원인을 조사한다
→ 가설을 세운다
→ 작은 실험으로 검증한다
→ 원리를 다시 구현한다
→ 다른 문제에 적용한다
→ 더 깊은 의문이 생긴다
```

## 1. 전체 학습 구조

4개의 축으로 구성

```txt
프로젝트 축    실제로 작동하는 것을 만든다
실험 축        궁금한 현상을 최소한의 코드로 격리한다
지식 지도 축   발견한 원리를 분류하고 서로 연결한다
검증 축        예측, 설명, 변형, 재구현으로 이해를 증명한다
```

따라서 모든 학습은 다음 세 규모에서 동시에 진행되어야 한다.

| 규모 | 단위                            | 목적                  |
| ---- | ------------------------------- | --------------------- |
| 미시 | 5~30줄 실험 코드                | 하나의 현상을 격리    |
| 중간 | 자료구조·라이브러리·도구        | 여러 원리를 결합      |
| 거시 | 인터프리터·서버·런타임 프로젝트 | 전체 실행 구조를 통합 |

## 2. 기본 학습 단위: 순환적 탐구

개념에서 학습이 시작되는 것이 아니라 하나의 현상 또는 문제에서 시작

### 1단계: 먼저 시도한다.

예시:

```txt
- debounce를 구현한다
- Promise 실행 순서를 예상한다
- LRU Cache를 구현한다
- 객체 복사 함수를 만든다
- 재귀 없이 DFS를 구현한다
- 간단한 표현식 계산기를 만든다
- 파일을 여러 개 동시에 읽는 프로그램을 만든다
- 메모리 누수가 발생하는 코드를 만든다
```

### 2단계: 실행 전에 예측한다

실행하기 전에 반드시 다음을 적어본다.

```txt
- 출력 순서
- 반환값
- 발생할 오류
- 생성되는 변수와 객체
- 함수 호출 순서
- 변경되는 상태
- 비동기 작업의 실행 순서
- 시간과 공간 복잡도
```

> 틀린 예측이 가장 가치 있는 학습 재료다.
> 머릿 속의 모델을 발전시키는 것이 중요하다.

### 3단계: 관찰한다.

단순히 최종 출력만 확인하지 않는다.

다음 도구를 사용해 실행 과정 자체를 관찰한다.

```txt
- debugger breakpoint
- step into / step over
- call stack
- scope inspector
- watch expression
- console.trace
- performance profiler
- heap snapshot
- Node.js inspector
- 테스트 코드
```

관찰 대상은 다음과 같다.

```txt
현재 실행 중인 함수는 무엇인가?
어떤 변수 바인딩이 존재하는가?
this는 무엇인가?
어떤 객체가 다른 객체를 참조하는가?
어느 시점에 Promise callback이 실행되는가?
함수 종료 후에도 어떤 값이 남아 있는가?
```

### 4단계: 어긋난 지점을 수집한다.

예상과 실제가 어긋난 지점을 질문으로 바꾼다.

예시:

```txt
왜 이 함수는 반환된 뒤에도 count 값을 유지하는가?
왜 setTimeout보다 Promise.then이 먼저 실행되는가?
왜 배열의 length가 실제 원소 개수와 다를 수 있는가?
왜 같은 객체 구조를 반복 생성하면 더 빨라질 수 있는가?
왜 await 뒤의 코드는 현재 함수 호출 안에서 바로 실행되지 않는가?
```

> 질문은 반드시 관찰 가능한 현상을 포함해야 한다.

### 5단계: 질문을 지식 지도에 배치한다.

각 질문에 태그를 붙인다.

#### 지식 영역 태그

```txt
JS-SYNTAX       문법과 평가
JS-VALUE        값, 타입, 변환
JS-SCOPE        바인딩, 스코프, 클로저
JS-EXECUTION    실행 컨텍스트와 호출
JS-FUNCTION     함수와 this
JS-OBJECT       객체와 프로토타입
JS-ASYNC        Promise, async/await
HOST-BROWSER    브라우저 환경
HOST-NODE       Node.js 환경
ENGINE          파싱, JIT, GC, 객체 표현
DS              자료구조
ALGORITHM       알고리즘과 복잡도
OS              프로세스, 스레드, I/O
NETWORK         HTTP, TCP, 스트림
DESIGN          설계와 모듈 경계
TOOL            디버깅, 테스트, 빌드
```

#### 지식 성격 태그

```txt
[S] ECMAScript 언어 규칙
[H] 브라우저나 Node.js의 호스트 규칙
[E] V8 등 엔진 구현
[C] 컴퓨터 과학의 일반 원리
[F] 프레임워크 규칙
```

예시:

```txt
질문:
왜 Promise.then이 setTimeout보다 먼저 실행되는가?

분류:
JS-ASYNC
HOST-BROWSER
[S]
[H]
```

### 6단계: 최소 이론을 학습한다.

질문을 답하는 데 필요한 범위 정도만 공부한다.

예를 들어, Promise 실행 순서가 궁금하다면 처음부터 비동기 JavaScript 전체를 읽지 않는다.

```txt
1. 호출 스택
2. Promise reaction
3. microtask
4. task
5. 현재 호스트의 event loop
```

까지만 조사한다.

이를 **Just-In-Time Theory**, 즉 필요 시점 이론 학습으로 운영한다.

다만 한 질문에서 인접한 개념이 드러나면 지식 지도에 연결만 해두고, 당장 모두 공부하려 하지 않는다.

### 7단계: 가설을 세운다.

조사한 내용을 토대로 가설을 만든다.

```txt
가설:
현재 동기 코드가 끝난 뒤 Promise reaction이 microtask로 실행되고,
timer callback은 이후 task에서 실행되므로 Promise callback이 먼저 실행된다.
```

> 가설은 반드시 틀릴 수 있는 문장이어야 한다.

좋은 가설 예시:

```txt
동일한 브라우저 event loop iteration에서 현재 task가 끝나면
timer task보다 먼저 microtask checkpoint가 수행될 것이다.
```

### 8단계: 반증 실험을 만든다.

가설을 확인하는 실험보다 가설을 깨뜨릴 수 있는 실험을 만든다.

```js
console.log("A");

setTimeout(() => {
  console.log("B");

  queueMicrotask(() => {
    console.log("C");
  });
}, 0);

Promise.resolve().then(() => {
  console.log("D");

  setTimeout(() => {
    console.log("E");
  }, 0);
});

console.log("F");
```

그 다음 아래 목록을 시도한다.

```txt
- Promise를 중첩한다
- timer 내부에 microtask를 넣는다
- 브라우저와 Node.js에서 각각 실행한다
- process.nextTick을 추가한다
- 동기 작업을 길게 만든다
- 무한한 microtask 체인을 만든다
```

> 하나의 예제를 이해하는 것이 아니라, 원리가 유지되는 경계와 깨지는 경계를 찾는 것이다.

### 9단계: 원리를 재구현한다.

학습한 개념을 축소된 형태로 직접 구현한다.

| 학습 개념   | 재구현 과제                              |
| ----------- | ---------------------------------------- |
| 클로저      | 렉시컬 환경을 가진 작은 함수 평가기      |
| Promise     | 상태와 reaction queue를 가진 MiniPromise |
| 이벤트 루프 | task queue와 microtask queue 시뮬레이터  |
| 프로토타입  | 부모 객체를 순회하는 속성 탐색 함수      |
| `new`       | 생성자 호출을 흉내 내는 함수             |
| iterator    | `next()` 상태 기계                       |
| 모듈        | 의존성 그래프를 읽는 작은 로더           |
| GC          | 객체 그래프의 mark-and-sweep 시뮬레이터  |
| 해시 테이블 | 충돌 처리를 포함한 직접 구현             |
| async queue | 동시 실행 수를 제한하는 작업 큐          |

> 실제 명세와 완전히 같을 필요는 없다. 핵심 작동 원리를 재현하는 것이 목적이다.

### 10단계: 다른 상황으로 전이한다.

같은 원리를 전혀 다른 문제에 적용한다.

예:

```txt
클로저
→ debounce
→ React event handler
→ 메모리 누수
→ 모듈 캡슐화

큐
→ BFS
→ 이벤트 루프
→ 작업 스케줄러
→ 메시지 브로커

그래프
→ SNS 관계
→ 모듈 의존성
→ 빌드 순서
→ 객체 참조 구조
→ GC reachability
```

> 한 개념을 한 상황에서만 이해하면 기억이다. 여러 상황에서 전이할 수 있으면 구조적 이해다.

## 3. 학습 기록 체계

모든 탐구는 다음 형식으로 기록한다.

```markdown
# 탐구 제목

## 1. 현상

무엇을 만들거나 실행했는가?

## 2. 실행 전 예상

출력, 반환값, 실행 순서, 복잡도를 어떻게 예상했는가?

## 3. 실제 결과

실제로 무엇이 발생했는가?

## 4. 차이

예상과 실제가 어디서 달랐는가?

## 5. 질문

정확히 무엇이 궁금한가?

## 6. 분류

- 지식 영역:
- 규칙 종류: [S] / [H] / [E] / [C] / [F]

## 7. 가설

현재 원인을 어떻게 추정하는가?

## 8. 실험

가설을 검증하거나 반박하기 위해 무엇을 변경했는가?

## 9. 결과

실험 결과는 무엇인가?

## 10. 현재 이해

작동 과정을 자신의 말로 설명한다.

## 11. 재구현

어떤 축소 모델이나 코드를 직접 만들었는가?

## 12. 전이

이 원리를 다른 어디에 적용할 수 있는가?

## 13. 미해결 질문

아직 남은 의문은 무엇인가?
```

> 이 기록은 일반적인 공부 노트가 아니라 연구 기록이어야 한다.

## 4. 비선형 학습을 가능하게 하는 프로젝트 군

### 프로젝트 A: JavaScript 실행 추적기

사용자가 입력한 JavaScript 코드를 실제로 실행하지 않고, 예상 실행 과정을 사람이 작성하도록 돕는 구조

초기 기능:

```txt
- 코드를 입력한다
- 선언 목록을 표시한다
- 함수 호출 순서를 기록한다
- 예상 출력값을 입력한다
- 실제 결과와 비교한다
```

자연스럽게 발생하는 학습:

```txt
문법
AST
평가 순서
스코프
호이스팅
클로저
함수 호출
예외
디버깅
```

확장 아이디어:

```txt
- Babel parser로 AST 시각화
- 변수 바인딩 변화 추적
- 객체 참조 그래프 표시
- task와 microtask 타임라인 표시
```

### 프로젝트 B: 작은 JavaScript 인터프리터

지원 문법을 매우 작게 시작

```javascript
let x = 10;
let y = x * 2;
y + 3;
```

첫 구현:

```txt
Tokenizer
→ Parser
→ AST
→ Evaluator
→ Environment
```

이후 확장:

```txt
조건문
→ 함수
→ 중첩 스코프
→ 클로저
→ 객체
→ this
→ 프로토타입
→ 예외
→ Promise 유사 모델
```

연결되는 영역:

```txt
프로그래밍 언어
컴파일러
자료구조
재귀
트리 순회
스택
메모리
실행 컨텍스트
```

> 이 프로젝트는 전체 과정의 가장 강력한 중심축이다.

### 프로젝트 C: 이벤트 루프 시뮬레이터

다음과 같은 API를 가진 축소 런타임을 만든다.

```js
runtime.run(() => {
  runtime.queueTask(taskA);
  runtime.queueMicrotask(microtaskA);
});
```

내부 구조:

```txt
Call Stack
Task Queue
Microtask Queue
Timer Queue
Clock
```

연결되는 영역:

```txt
Promise
async/await
이벤트 루프
큐
우선순위
동시성
starvation
브라우저와 Node.js 차이
운영체제 스케줄링
```

확장:

```txt
- microtask 무한 반복 감지
- timer clock 구현
- I/O 완료 이벤트 구현
- Node.js event loop phase 흉내 내기
- 시각적 타임라인 출력
```

### 프로젝트 D: 자료구조 라이브러리

JavaScript 기본 `Array`, `Map`, `Set`에 의존하지 않는 구현을 일부 만들어 본다.

```txt
Stack
Queue
Deque
LinkedList
HashMap
BinarySearchTree
Heap
Trie
Graph
Union-Find
LRU Cache
```

각 구현마다 반드시 포함한다.

```txt
- 불변식
- 시간 복잡도
- 공간 복잡도
- 단위 테스트
- 실패 입력
- 반복자
- 메모리 참조 구조
```

자료구조를 구현한 뒤 실제 문제에 연결한다.

| 자료구조    | 적용 프로젝트      |
| ----------- | ------------------ |
| Queue       | 작업 스케줄러      |
| Heap        | 우선순위 작업 큐   |
| Graph       | 모듈 의존성 분석기 |
| Trie        | 자동 완성          |
| LRU Cache   | HTTP 캐시          |
| Union-Find  | 네트워크 연결 그룹 |
| Ring Buffer | 로그 저장소        |

### 프로젝트 E: 비동기 작업 실행기

다음 기능을 점진적으로 구현한다.

```txt

- retry
- cancellation
- priority
- dependency
- backpressure
```

```js
queue.add(fetchUser, {

```

```txt

상태 기계
오류 처리
race condition
네트워크
재시도 전략
멱등성
```

### 프로젝트 G: 작은 모듈 로더와 번들러

```txt
→ 순환 참조 감지

```

연결되는 영역:


### 프로젝트 H: 메모리 누수 연구소

일부러 메모리 누수를 발생시키고 관찰한다.

```txt
- 해제되지 않은 이벤트 리스너
- 계속 쌓이는 배열
- 캐시에 남은 객체
- 클로저가 보존하는 큰 객체
- 종료되지 않은 timer
- 연결이 끊긴 DOM 노드
```

과정:

```txt
1. 누수를 만든다
2. 메모리 사용량을 측정한다
3. heap snapshot을 찍는다
4. retaining path를 찾는다
5. 원인을 수정한다
6. 다시 측정한다
```

연결되는 영역:

```txt
클로저
객체 그래프
GC
reachability
WeakMap
이벤트
DOM
성능 프로파일링
```
