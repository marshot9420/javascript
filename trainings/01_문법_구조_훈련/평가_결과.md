### 내 답안:

```js

```

```txt
전체: 표현식 문
내부: 특수 값 리터럴 `null`
```

### 평가:

## 문제 5

### 내 답안:

## 문제 5

```js
undefined;
```

```txt
전체: 표현식 문
내부: 특수 값 리터럴 `undefined`
값: 내부 표현식의 값은 undefined 값 `undefined`
```

### 평가:

`undefined`는 리터럴이 아니라 **식별자 참조 표현식**이다.

일반적인 전역 환경에서는 그 값이 `undefined` 값이다.

코드 `undefined`
→ 식별자 참조
→ 바인딩에서 값을 읽음
→ undefined 값

따라서 다음 둘은 평가 결과는 비슷해 보여도 문법적으로 다르다.

```js
null; // null 리터럴 표현식
undefined; // 식별자 참조 표현식
```

또한 `undefined`라는 이름은 문맥에 따라 다른 바인딩으로 가려질 수도 있다.

```js
function run(undefined) {
  console.log(undefined);
}

run(10);
```

이 함수 내부의 `undefined`는 숫자 값 `10`을 가진 매개변수를 참조한다. 이것이 `undefined`가 리터럴이 아니라 이름이라는 강력한 증거이다.

## 문제 7

### 내 답안:

## 문제 7

```js
[1, 2, 3];
```

```txt
전체: 표현식 문
내부: 배열 리터럴 표현식 `[1, 2, 3]`
값: 내부 표현식의 값은 배열 값 `[1, 2, 3]`
```

### 평가:

문법 판정은 정확하나, 배열은 별도의 원시값 종류가 아니라 **객체값**이다.

```txt
전체: 표현식 문
내부: 배열 리터럴 표현식 `[1, 2, 3]`
값: 내부 표현식을 평가하여 생성된 Array 객체값
```

중요한 구분은 다음과 같다.

```txt
[1, 2, 3]: 배열 리터럴 표현식
평가 결과: 새로 생성된 Array 객체
```

따라서 같은 배열 리터럴을 두 번 평가하면 서로 다른 객체가 생성된다.

```js
[1, 2, 3] === [1, 2, 3]; // false
```

## 문제 8

### 내 답안:

```js
({ name: "Mars" });
```

```txt
전체: 표현식 문
내부: 표현식이자 독립적인 실행문
값: 내부 표현식의 값은 객체 값 `{ name: "Mars" }`
```

### 평가:

전체와 값은 맞지만 내부 판정이 불명확.

`표현식이자 독립적인 실행문`은 전체 구조와 내부 구조를 섞어 표현한 것이다.

정확하게는 다음과 같다.

```txt
전체: 표현식 문
내부: 괄호로 묶인 객체 리터럴 표현식 `({ name: "Mars" })`
값: 내부 표현식을 평가하여 생성된 객체값 `{ name: "Mars" }`
```

조금 더 분해하면:

```txt
표현식 문
└─ 괄호로 묶인 표현식
   └─ 객체 리터럴 표현식
      └─ 프로퍼티
         ├─ 프로퍼티 이름: name
         └─ 문자열 리터럴 표현식: "Mars"
```

괄호는 객체값을 만드는 문법이 아니다. `{`가 문장의 시작에서 블록으로 해석되는 것을 막고, 객체 리터럴을 표현식으로 해석하도록 문맥을 만들어 준다.

## GPT 평가:

전체적으로 표현식의 종류와 평가 결과는 잘 구분하셨습니다. 주요 오류는 16번이며, 18·20번은 바깥 단위의 명칭을 바로잡아야 합니다. 17·19번은 값과 상태 변화를 조금 더 엄밀히 분리하면 됩니다.

다만 먼저 문제 구성 자체의 중요한 문제를 바로잡아야 합니다.

세미콜론 유무만으로 표현식과 표현식 문을 나눌 수는 없습니다

제가 앞서 문제를 다음처럼 나눈 것은 실제 JavaScript 소스 기준으로는 부정확했습니다.

```js
1 + 2;
```

```js
1 + 2;
```

첫 번째 코드를 단순한 표현식 조각으로 제시했다면 덧셈 표현식이라고 볼 수 있습니다. 하지만 이것을 완전한 Script의 소스 코드로 실행한다면 입력 끝에서 ASI가 적용되므로 둘 다 표현식 문입니다.

```txt
표현식 조각으로 분석:
1 + 2 → 덧셈 표현식

완전한 프로그램의 한 줄로 분석:
1 + 2 → 표현식 문
1 + 2; → 표현식 문
```

따라서 홀수 문제는 “이 코드를 표현식 위치에 놓인 문법 조각으로 본다”는 전제에서 채점하겠습니다. 실제 코드에서는 세미콜론이 없다고 문이 아닌 것이 아닙니다.

```txt
전체: 함수 호출 표현식
```


## 문제 17

### 내 답안:

```js
value = 10;
```

```txt
전체: 변수 할당 표현식
내부: 식별자 `value`에 값 `10`을 할당하는 표현식
값: 변수 `value`에 바인딩된 값 `10`
```

### 평가:

전체가 할당 표현식이라는 판정은 맞다. 다만 `변수 할당 표현식`보다는 단순히 **할당 표현식**이라고 하는 것이 정확하다.

또한 할당 표현식의 **평가 결과**와 할당으로 발생하는 **상태 변화**를 구분해야 한다.

```txt
전체: 할당 표현식
내부:
- 할당 대상: 식별자 참조 `value`
- 오른쪽: 숫자 리터럴 표현식 `10`
값: 할당 표현식의 평가 결과는 숫자 값 `10`
상태 변화: `value`가 참조하는 바인딩에 숫자 값 `10`이 저장됨
```

다음 답안에서는 평가 결과와 상태 변화가 섞여 있다.

```txt
값: 변수 `value`에 바인딩된 값 `10`
```

할당 표현식 자체가 만들어 내는 결과는 숫자 값 `10`이다. 그와 별개로 `value`에 `10`이 저장된다.

```txt
평가 결과: 숫자 값 `10`
상태 변화: `value`에 숫자 값 `10` 저장
```

또한 코드만 보고 `value`를 반드시 변수라고 단정하기보다는, **할당 대상이 되는 식별자 참조**라고 표현하는 것이 더 정확하다.

## 문제 18

### 내 답안:

```js
value = 10;
```

```txt
전체: 변수 할당 표현식 문
내부: 식별자 `value`에 값 `10`을 할당하는 표현식
값: 변수 `value`에 바인딩된 값 `10`
```

### 평가:

전체를 `변수 할당 표현식 문`이라고 표현했지만, 문법상의 바깥 단위는 단순히 **표현식 문**이다.

그 표현식 문 내부에 할당 표현식이 들어 있다.

```txt
전체: 표현식 문
내부: 할당 표현식 `value = 10`
값: 내부 할당 표현식의 평가 결과는 숫자 값 `10`
상태 변화: `value`가 참조하는 바인딩에 숫자 값 `10`이 저장됨
```

비교하면 다음과 같다.

```txt
value = 10     할당 표현식
value = 10;    할당 표현식을 포함한 표현식 문
```

할당 표현식이 들어 있다고 해서 `할당 표현식 문`이라는 별도의 문 종류가 되는 것은 아니다.

```txt
표현식 문
└─ 할당 표현식
   ├─ 할당 대상: `value`
   └─ 오른쪽 표현식: `10`
```

## 문제 19

### 내 답안:

```js
count++;
```

```txt
전체: 후위 증가 연산자 표현식
내부: 변수 `count`의 값에서 `1`을 증가시키는 후위 증가 연산자 표현식
값: `count`의 값을 먼저 반환한 후 `1`을 증가시키므로, 본래 `count`에 바인딩된 값
```

### 평가:

전체가 후위 증가 표현식이라는 판정과, 증가 이전의 값을 결과로 만든다는 이해는 맞다.

문법 용어로는 **후위 갱신 표현식**이라고 정리할 수 있다.

```txt
전체: 후위 갱신 표현식
내부:
- 갱신 대상: 식별자 참조 `count`
- 연산자: 후위 증가 연산자 `++`
값: 증가 연산을 적용하기 전의 숫자형 값
상태 변화: `count`에는 1 증가한 숫자형 값이 저장됨
```

예를 들어 `count`가 숫자 값 `10`이라면 다음과 같다.

```txt
표현식의 평가 결과: 숫자 값 `10`
변경된 count의 값: 숫자 값 `11`
```

다만 평가 결과를 단순히 `본래 count에 바인딩된 값`이라고 표현하면 일부 경우에는 정확하지 않을 수 있다.

```js
let count = "1";
const result = count++;
```

이 경우 결과는 다음과 같다.

```txt
result: 숫자 값 `1`
count: 숫자 값 `2`
```

원래 `count`에 들어 있던 값은 문자열 값 `"1"`이지만, `++` 연산 과정에서 숫자형 값으로 변환된다.

따라서 다음 표현이 더 정확하다.

```txt
값: 숫자형 변환 후, 증가하기 전의 값
상태 변화: 증가한 숫자형 값이 `count`에 저장됨
```

## 문제 20

### 내 답안:

```js
count++;
```

```txt
전체: 후위 증가 연산자 표현식 문

```

### 평가:

전체를 `후위 증가 연산자 표현식 문`이라고 작성했지만, 바깥 문법 단위는 단순히 **표현식 문**이다.

그 내부에 후위 갱신 표현식이 들어 있다.

```txt
전체: 표현식 문
내부: 후위 갱신 표현식 `count++`
값: 내부 표현식의 평가 결과는 증가하기 전의 숫자형 값
상태 변화: `count`에는 1 증가한 숫자형 값이 저장됨
```

구조는 다음과 같다.

```txt
표현식 문
└─ 후위 갱신 표현식
   ├─ 갱신 대상: 식별자 참조 `count`
   └─ 후위 증가 연산자: `++`
```

비교하면 다음과 같다.

```txt
count++     후위 갱신 표현식
count++;    후위 갱신 표현식을 포함한 표현식 문
```

`count`가 숫자 값 `10`이라면 다음과 같이 구분할 수 있다.

```txt
내부 표현식의 평가 결과: 숫자 값 `10`
상태 변화: `count`에 숫자 값 `11` 저장
```

## 문제 17 ~ 20의 핵심 교정

### 표현식과 표현식 문

```txt
value = 10     할당 표현식
value = 10;    표현식 문
               └─ 할당 표현식

count++        후위 갱신 표현식
count++;       표현식 문
               └─ 후위 갱신 표현식
```

### 평가 결과와 상태 변화

```js
value = 10;
```

```txt
평가 결과: 숫자 값 `10`
상태 변화: `value`에 숫자 값 `10` 저장
```

```js
count++;
```

```txt
평가 결과: 증가하기 전의 숫자형 값
상태 변화: 증가한 숫자형 값을 `count`에 저장
```

표현식이 만들어 내는 값과 표현식의 실행으로 바인딩이 변경되는 것은 서로 다른 결과이므로 분리해서 보아야 한다.
